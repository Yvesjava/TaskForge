# TaskForge 产品文档

## 1. 文档概述

TaskForge 是一套基于文档驱动开发的无人值守 AI Agent 研发流水线控制台。

### 1.1 背景与痛点

在日常敏捷研发流程中，开发者在本地与 AI 沟通梳理业务需求与架构设计后，通常需要手动拉取代码、切分支、在 IDE 中反复提示 AI 编写代码、手动运行测试、提交代码、发起 Pull Request 并通知测试与团队成员。该过程存在多仓协同繁琐、本地资源占用高、缺乏自动化单测验收机制以及人工干预流程断层等痛点。

### 1.2 产品定位

TaskForge 打造一套**基于 Spec-Driven Development（文档驱动开发）的无人值守 AI Agent 研发流水线控制台**。
系统通过接收本地结构化需求文档（Markdown），自动将其入队调度，在独立物理沙箱（Git Worktree）中拉取多工程代码并构建聚合空间，驱动 Codex 批量执行编码与自实验收，并通过企业即时通讯（企微/飞书）推动人工验收，最终实现一键合并主分支并回收资源的完整闭环。

---

## 2. 用户角色与核心场景

### 2.1 用户角色

* **研发工程师**：本地与 AI 梳理业务后，将规范文档投递至系统；在系统或移动端审核 Diff 并执行验收。
* **项目管理员**：维护底层代码仓（Project Registry）元数据，配置 Git 认证与构建命令。

### 2.2 核心业务流

1. **本地沟通与投递**：工程师在本地通过 AI 工具沟通形成标准 Markdown 需求文档，调用 API 投递至系统。
2. **队列生命周期管控**：任务在未被消费前，工程师可在 Web 页面进行**暂停、继续编辑（含执行细节/超时/参数）、恢复排队、取消、软删除、初态重置**。
3. **沙箱构建与自动执行**：Worker 获取排队任务，基于 Git Worktree 快速挂载跨仓聚合工作区（如同时包含后端与前端），启动 Codex CLI 执行计划，并在沙箱中串行跑通验收测试脚本。
4. **提交与验收通知**：自测通过后，系统自动向各仓推送分支，并在企业微信/飞书群发送带有代码改动统计与测试报告的交互式卡片。
5. **一键合并与清理**：工程师点击【已验收】后，系统调用 Git 平台 API 自动将代码合并至各仓主分支，并彻底销毁工作区物理目录。

## 3. 详细功能需求

### 3.1 项目资产管理 (Project Registry)

* **仓储维护**：支持增删改查前端、后端等多代码仓的项目唯一编码、项目名称、Git 仓库地址（SSH/HTTP）、默认主分支（如 `main` 或 `master`）、构建工具类型（`maven`、`pnpm`、`gradle`、`go` 等）及基础单测命令。
* **状态开关**：支持启用/停用特定代码仓；任务只能引用已启用的项目资产。
* **资产引用**：任务通过项目编码引用仓库，系统在投递和调度前校验项目存在、基线分支有效以及子目录映射不冲突。

### 3.2 任务队列控制面

* **任务状态流转**：
* `PENDING` (待执行)：进入队列等待调度。
* `PAUSED` (已暂停)：任务挂起，调度器跳过。支持修改计划明细、执行参数、重置状态。
* `RUNNING` (执行中)：Worker 正在拉取代码、驱动 Codex 或执行测试。
* `WAITING_ACCEPTANCE` (待验收)：Codex 自测试通过，分支推送完毕，已发送通知等待人工确认。
* `ACCEPTED` (已验收)：人工点击验收，触发各仓主分支自动合并。
* `COMPLETED` (已完成)：所有代码仓合并成功，工作区和临时资源已回收，任务归档。
* `REJECTED` (已打回)：人工验收不通过并附带反馈，可重新派发或转人工接管。
* `CANCELED` (已取消)：移出执行队列，支持重新入队与软删除。
* `DELETED` (已软删除)：从用户视图中隐藏，保留数据库审计痕迹。
* `FAILED` (执行失败)：自测未通过或执行超时，保留错误日志供排查。
* `RESETTING` (重置中)：正在终止残留进程、清理工作区和分支，期间禁止重复操作。
* `MERGE_CONFLICT_PENDING_MANUAL` (合并冲突待处理)：至少一个代码仓无法无冲突合并，暂停自动合并并通知人工介入。


* **未执行控制动作**：
* **暂停/恢复**：排队期可随时暂停，暂停期调度器不消费；恢复后重新按优先级排队。
* **详情修改**：暂停状态下支持在 Web 界面在线修改 Markdown 文档中的“执行计划”、“验收步骤”、“验收标准”，以及超时时间、Codex 模型/参数、基线分支、优先级和前置任务依赖。保存时使用文档版本号进行乐观锁校验，避免覆盖他人修改。
* **调度顺序与抢占**：调度器仅消费未软删除且状态为 `PENDING` 的任务，按优先级升序、创建时间升序取任务；任务从 `PENDING` 抢占为 `RUNNING` 必须原子校验，暂停或取消与抢占同时发生时，未成功抢占的 Worker 必须放弃执行。
* **重置状态 (Reset)**：仅针对暂停任务执行**彻底清零**。系统先进入 `RESETTING`，强制终止残留进程组，再注销并物理删除所有 Worktree 目录，删除各仓远端和本地特性分支，清空 AI 日志、Diff、重试次数和耗时数据，但保留用户任务文档及其版本历史。完成后默认恢复 `PENDING`，也可选择保留 `PAUSED` 等待继续编辑；下次执行必须从最新基线重新创建分支。
* **重置防呆**：重置前必须二次确认，并保证操作幂等；即使工作区或分支已不存在，也应完成元数据清理并返回成功结果。
* **取消与软删除**：取消任务后冻结任务内容并保留操作审计；重新入队支持原位恢复为 `PENDING` 或克隆为全新任务编号。仅 `CANCELED` 状态允许执行软删除，软删除后默认查询和统计均隐藏，但数据库保留审计记录。



### 3.3 多仓聚合沙箱与自验闭环

* **多仓编排**：支持单个任务同时定义多个子工程（如 `backend` 与 `frontend`），并在同一独立工作区（`dirA`）下挂载各项目；每个项目独立配置 `baseBranch` 与 `subDir`，所有项目默认使用同一任务特性分支名。
* **聚合工作区**：根目录写入 `.ai/task.md` 任务文档，子目录分别对应各 Git Worktree，使 Codex 能同时读取跨仓接口、类型和业务上下文。
* **Codex 自测约束**：参考 Symphony 协议，以非交互模式启动 Codex，约束其必须按任务文档执行计划并运行所有验收步骤。仅当所有项目的验收命令退出码（Exit Code）均为 0 时，才允许自动 Git Commit 与 Push。
* **执行监控与重试**：实时采集 Codex、编译和测试的 stdout/stderr；编译或测试失败时允许基于错误输出自动纠错重试，最多 2 次，仍失败则标记 `FAILED` 并保留完整日志。
* **超时熔断**：配置单任务最大运行时长（如 30-45 分钟），超时自动终止整个进程组并标记 `FAILED`，防止僵尸进程和残留工作区。

### 3.4 协同通知与自动合并

* **卡片推送**：集成企业微信/飞书机器人 Webhook，在任务进入 `WAITING_ACCEPTANCE` 时，推送包含任务 ID、各仓分支链接、变更文件清单、Diff 统计、验收命令输出和测试结果的交互卡片。
* **双通道验收**：支持在 Web 控制台或企微/飞书卡片上一键点击【确认验收】与【打回】；打回必须记录反馈意见并回传给下一次执行。
* **合并平台**：支持通过 GitLab MR、GitHub PR 或兼容的 Git 平台 API 发起合并，默认采用 Fast-Forward 或 Squash Merge。
* **原子合并 (All-or-Nothing)**：多仓任务必须在所有仓均可无冲突合入时才执行合并；任一仓冲突时进入 `MERGE_CONFLICT_PENDING_MANUAL`，阻断其他仓合并并通知人工介入，禁止形成半完成状态。合并完成后级联清理所有 Worktree 并将任务置为 `COMPLETED`。

### 3.5 任务文档契约与投递

* **投递接口**：提供 `POST /api/v1/tasks/submit` 接收本地 Markdown 文档，系统生成任务编号并写入持久化队列；接口返回任务编号、当前状态和文档版本。
* **YAML Front Matter**：文档必须包含 `taskId`、`title`、`targetBranch` 和 `timeoutMinutes`；单仓任务使用 `repoUrl`、`baseBranch`，多仓任务使用 `projects` 列表，列表项至少包含 `code`、`baseBranch`、`subDir`。`priority`、`dependsOnTaskId` 和 Codex 模型/参数为可选字段。
* **标准 Markdown 小节**：正文必须包含“需求目标与上下文”、“任务执行计划（Execution Plan）”、“验收步骤（Verification Steps）”和“验收标准（Acceptance Criteria）”；执行计划和验收标准使用可勾选清单，验收步骤必须是可执行命令或明确检查项。
* **文档校验**：投递和暂停恢复前校验 Front Matter、项目编码、分支及必需小节；校验失败时拒绝入队并返回具体错误，不得让 Worker 在运行中才发现文档不完整。

示例：

```markdown
---
taskId: "TASK-20261001-088"
title: "会员充值优惠券抵扣全栈支持"
targetBranch: "feature/TASK-20261001-088"
timeoutMinutes: 45
projects:
  - code: "backend-service"
    baseBranch: "main"
    subDir: "backend"
  - code: "frontend-portal"
    baseBranch: "main"
    subDir: "frontend"
---

# 需求目标与上下文

## 任务执行计划
- [ ] 完成后端接口与测试
- [ ] 完成前端页面与类型定义

## 验收步骤
1. `cd backend && mvn test`
2. `cd frontend && pnpm run type-check && pnpm test`

## 验收标准
- [ ] 所有验收命令通过
- [ ] 不破坏既有功能
```

### 3.6 执行结果与审计

* **结果记录**：任务详情必须展示执行日志、测试报告、Diff 统计、修改文件清单、分支地址、重试次数、开始/结束时间和总耗时。
* **失败可排查**：`FAILED`、打回和合并冲突任务保留错误堆栈及最后一次执行上下文，支持从失败节点重新执行或转人工处理。
* **操作审计**：暂停、编辑、恢复、取消、重置、重投、验收、打回和删除均记录操作人、时间、前后状态、反馈意见及文档版本。
