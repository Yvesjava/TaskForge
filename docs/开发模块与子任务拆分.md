# TaskForge 开发模块与子任务拆分

## 1. 文档目的

本文档把 [产品文档](产品文档.md) 和 [技术开发与架构设计文档](技术开发与架构设计文档.md) 中的需求拆成可独立排期、实现和验收的开发模块。模块是长期维护的边界，子任务是一次迭代中可交付的最小工作单元。

后续创建开发任务时，任务编号使用 `模块编号-序号` 格式，例如 `TASK-DOC-01`。子任务不得跨越多个模块的核心职责；确需跨模块联调时，应明确依赖和联调产物。

## 2. 拆分原则

1. **按业务边界拆分**：数据、控制面、调度、执行、协同和前端分别负责自己的模型与接口。
2. **按依赖顺序交付**：先完成数据契约和基础能力，再实现状态流转，最后接入外部平台和完整 UI。
3. **每个子任务有可验证产物**：代码、数据库迁移、接口契约、测试或运行手册至少交付一种，并写出明确验收条件。
4. **状态变更集中管理**：任务状态只能经过状态机服务和审计记录变更，控制器、Worker、通知回调不得直接改状态。
5. **安全能力横向覆盖**：凭证、路径、进程、日志和 Webhook 的安全约束从第一版实现，不作为上线前临时补丁。
6. **先做最小闭环**：第一阶段先跑通“投递文档 -> 入队 -> 执行 -> 自验 -> 待验收”的单 Worker 单仓闭环，再扩展多仓、通知和自动合并。

## 3. 模块总览

| 模块编号 | 模块名称 | 主要边界 | 关键依赖 | 主要交付物 |
| --- | --- | --- | --- | --- |
| `BASE` | 工程基线与环境 | Maven、前端、Docker、本地配置和构建规范 | 无 | 可重复启动的开发环境、构建命令 |
| `DATA` | 数据底座 | 表结构、迁移、DO/Mapper、审计字段和索引 | `BASE` | 数据库迁移、持久化模型、数据访问测试 |
| `PROJECT` | 项目资产管理 | 代码仓元数据、启停、权限和引用校验 | `DATA` | 项目 CRUD API、项目管理页面 |
| `DOC` | 任务文档契约 | Markdown、Front Matter、版本和投递校验 | `DATA`, `PROJECT` | 文档解析器、校验器、投递 API |
| `TASK` | 任务控制面与状态机 | 生命周期动作、状态转换、幂等和操作审计 | `DATA`, `DOC` | 状态机服务、控制面 API |
| `SCHED` | 调度与 Worker 租约 | 抢占、心跳、租约、取消和超时恢复 | `TASK` | 调度器、租约服务、恢复任务 |
| `WORK` | 多仓工作区与 Git | Bare Repo、Worktree、分支、路径和清理 | `PROJECT`, `SCHED` | 工作区编排器、Git 适配器、清理器 |
| `EXEC` | AI 执行与自验 | Workflow、Codex 子进程、命令、重试和结果 | `WORK`, `SCHED` | Worker 执行链、日志和测试报告 |
| `NOTICE` | 通知与回调 | 企微/飞书卡片、签名、重试和回调幂等 | `TASK`, `EXEC` | Webhook 适配器、验收卡片和回调 API |
| `MERGE` | 多仓合并与收尾 | 预检、合并、冲突、回滚和资源回收 | `WORK`, `NOTICE`, `TASK` | Git 平台适配器、合并编排器 |
| `WEB` | 前端控制台 | 项目、任务、文档、Diff、日志和验收操作 | `PROJECT`, `TASK`, `EXEC`, `MERGE` | Vue 页面、API 类型和权限路由 |
| `OPS` | 安全与可观测性 | 凭证、脱敏、权限、追踪、指标和补偿 | 全部运行模块 | 安全策略、日志指标、告警和补偿任务 |
| `QA` | 测试与发布 | 单元、集成、端到端、灰度和回滚 | 全部模块 | 测试门禁、发布清单、灰度报告 |

## 4. 模块依赖关系

```text
BASE
  |
  v
DATA ---> PROJECT ----+
  |                   |
  +------> DOC -------+
                    v
                  TASK ---> SCHED ---> WORK ---> EXEC ---> NOTICE ---> MERGE
                    |        |         |         |          |          |
                    +--------+---------+---------+----------+----------+
                                         |
                                         v
                                        WEB

OPS 横向约束 DATA、TASK、SCHED、WORK、EXEC、NOTICE、MERGE 和 WEB
QA 在各模块具备可运行产物后执行，负责集成门禁和灰度发布
```

依赖规则：

- `DATA` 先于所有需要持久化的后端模块；数据库迁移和索引未通过前，不进入业务联调。
- `DOC` 和 `TASK` 先于 `SCHED`；调度器只消费经过文档契约校验、状态为 `PENDING` 的任务。
- `WORK` 先于 `EXEC`；Codex 不得直接操作宿主机任意目录，必须使用经过校验的任务工作区。
- `NOTICE` 与 `MERGE` 必须复用 `TASK` 的状态机和幂等服务，禁止在回调或 Git 适配器中自行推进状态。
- `WEB` 以已稳定的 API 契约为输入；页面可以并行开发，但必须使用接口 Mock 或契约测试。
- `OPS` 和 `QA` 从首个可运行模块开始跟进，不能全部推迟到最后一个里程碑。

## 5. 一级子任务目录

以下是每个模块的第一层子任务。每项仍可继续拆成实现、测试、文档和联调任务。

| 子任务 | 内容 | 验收产物 |
| --- | --- | --- |
| `TASK-BASE-01` | 注册 `yudao-module-agent` 的 Maven 模块和包结构 | 后端可跳过业务实现完成编译 |
| `TASK-BASE-02` | 固化 `local,taskforge` 配置、Docker Compose、MySQL/Redis 启动参数 | 新环境可按 README 启动并通过健康检查 |
| `TASK-BASE-03` | 统一前端 API 环境变量、端口和本地开发命令 | `pnpm dev` 能访问后端配置的 API 地址 |
| `TASK-BASE-04` | 建立格式、构建、日志和分支约定 | README、AGENTS.md 与实际命令一致 |

## 7. 子任务编写与验收模板

创建具体子任务时，至少填写以下内容：

```markdown
## TASK-<MODULE>-<NN> <任务标题>

- 模块：`<MODULE>`
- 目标：一句话说明要解决的问题
- 前置任务：列出已完成或必须先完成的任务编号
- 影响范围：后端模块、前端页面、数据库、外部平台
- 输入契约：接口、表、配置或文档
- 实现内容：列出实现边界，不扩展到其他模块
- 交付物：代码、迁移、接口文档、测试、运行手册
- 验收命令：可复制执行的命令
- 验收条件：可观察、可判断、不可含糊
- 风险与回滚：失败时如何清理或恢复
- 状态：`TODO` / `IN_PROGRESS` / `BLOCKED` / `DONE`
```

子任务完成必须满足：

1. 依赖任务已完成，或已经提供可替代的 Mock/契约。
2. 验收命令在干净环境或指定测试容器中可重复执行。
3. 数据库、状态机、外部副作用和敏感信息变更都有对应测试或审计说明。
4. 文档、API 示例、配置模板与实现保持一致。
5. 若改变产品行为或架构契约，同步更新产品文档或技术架构文档。

## 8. 当前拆分边界

第一批开发优先建立最小可运行闭环：`BASE -> DATA -> PROJECT -> DOC -> TASK -> SCHED -> WORK -> EXEC`。`NOTICE`、`MERGE`、`WEB`、`OPS` 和 `QA` 可以并行准备接口与测试，但不能绕过前述状态、租约和执行契约。

后续新增需求先归入现有模块；只有当一个模块出现独立数据模型、独立生命周期、独立权限边界或独立发布节奏时，才新增模块编号。模块编号一旦使用不得复用，子任务完成后保留记录和验收结果。
