## 1. 技术栈选型与系统架构

### 1.1 技术栈基准

* **项目名称**：TaskForge，面向多仓代码任务的文档驱动 AI 研发流水线控制台。
* **后端框架**：Java 17 + Spring Boot 3.x，在 `ruoyi-vue-pro` 项目中新增独立业务模块：`yudao-module-agent`。
* **前端框架**：Vue 3 + TypeScript + Vite + Element Plus，依托 `yudao-ui-admin-vue3` 实现可视化控制台。
* **任务调度与锁**：MySQL 8.0 原生 `FOR UPDATE SKIP LOCKED` 悲观锁无竞争并发调度；Redis 7.x 维护实时状态缓存与租约。
* **沙箱与版本控制**：宿主机维持 Bare Repo 缓存，基于 `git worktree` 实现毫秒级工作区创建与销毁。
* **沙箱资源隔离**：编译和测试命令优先运行在 Docker 容器或 Linux Cgroups 约束下，限制 CPU、内存和磁盘写入，避免 AI 生成命令污染 Worker 宿主机。
* **AI 运行层**：Codex CLI / Claude Code（支持非交互批处理模式），结合 Symphony 规范设计的 `WORKFLOW.md` 系统级提示词；通过 MCP 提供工程规则、数据库 Schema 和依赖版本等只读上下文。
* **进程控制**：Worker 负责捕获 stdout/stderr、维护进程组、执行硬超时终止和退出码校验，并为每个任务记录 worker 标识与租约。
* **协同集成**：通过企业微信/飞书 Webhook 推送验收卡片，通过 GitLab/GitHub/Gitea API 完成分支校验、合并和冲突查询。

### 3.2 任务消费调度器与并发锁实现

利用 Spring Task 定时拉取任务，结合 `FOR UPDATE SKIP LOCKED` 防重复消费，并支持多租户忽略。

生产实现必须把“捞取并抢占”放在独立短事务中，事务提交成功后再投递异步执行；不要在持有数据库行锁时启动 Codex 或 Git 操作。调度器和抢占服务拆成两个 Bean，避免 `@Transactional` 自调用失效：

```java
@Component
@Slf4j
public class AgentTaskScheduler {

    @Resource
    private AgentTaskClaimService taskClaimService;
    @Resource
    private AgentTaskExecutor taskExecutor;

    @Scheduled(fixedDelay = 3000)
    public void scheduleNextTask() {
        // 调度器使用 TenantUtils.executeIgnore(...) 包裹 claimNextTask，扫描所有租户的可执行任务
        taskClaimService.claimNextTask()
            .ifPresent(task -> {
                log.info("[TaskScheduler] 成功抢占任务 id: {}, 代次: {}",
                    task.getId(), task.getExecutionGeneration());
                // 此处已离开数据库事务；异步执行不得依赖行锁仍然存在
                taskExecutor.asyncExecute(task.getId(), task.getExecutionGeneration());
            });
    }
}

@Service
public class AgentTaskClaimService {

    @Transactional(rollbackFor = Exception.class)
    public Optional<AgentTaskDO> claimNextTask() {
        AgentTaskDO task = taskMapper.selectNextPendingTaskForUpdate();
        if (task == null) {
            return Optional.empty();
        }
        LocalDateTime now = LocalDateTime.now();
        long generation = task.getExecutionGeneration() + 1;
        int updated = taskMapper.claimPendingTask(
            task.getId(), workerIdentity.id(), now, now.plusMinutes(5), generation);
        if (updated != 1) {
            return Optional.empty();
        }
        task.setExecutionGeneration(generation);
        task.setWorkerId(workerIdentity.id());
        return Optional.of(task);
    }
}
```

对应的 MyBatis XML 查询片段（`SELECT` 与条件更新必须在同一个短事务内完成）：

```xml
<select id="selectNextPendingTaskForUpdate"
        resultType="cn.iocoder.yudao.module.agent.dal.dataobject.task.AgentTaskDO">
    SELECT *
    FROM agent_task
    WHERE status = 'PENDING'
      AND deleted = 0
      AND (depends_on_task_id IS NULL OR EXISTS (
          SELECT 1 FROM agent_task prerequisite
          WHERE prerequisite.id = agent_task.depends_on_task_id
            AND prerequisite.status = 'COMPLETED'
            AND prerequisite.deleted = 0
      ))
    ORDER BY priority ASC, create_time ASC
    LIMIT 1
    FOR UPDATE SKIP LOCKED
</select>

<update id="claimPendingTask">
    UPDATE agent_task
        SET status = 'RUNNING',
        started_time = #{startedTime},
        worker_id = #{workerId},
        lease_until = #{leaseUntil},
        execution_generation = #{executionGeneration},
        heartbeat_time = #{startedTime},
        update_time = NOW()
    WHERE id = #{id}
      AND status = 'PENDING'
      AND deleted = 0
</update>
```

Worker 只有在条件更新影响行数为 `1` 时才可以继续执行；影响行数为 `0` 表示任务已被暂停、取消或被其他 Worker 抢占。租约续期失败时，Worker 必须停止写入结果并进入清理流程。

控制面需要周期性扫描 `status = 'RUNNING' AND lease_until < NOW()` 的任务，将其标记为 `FAILED` 或送入人工恢复队列，并触发对应 Worker 的进程组清理。恢复动作必须带任务版本或执行代次，避免旧 Worker 在网络恢复后覆盖新一次执行结果。

#### 3.2.1 Redis 租约、Worker 心跳与超时恢复

MySQL 是任务状态的最终事实来源，Redis 只用于快速发现租约和广播取消信号。每次抢占任务后写入以下键，并把执行代次写入值中：

| Redis 键 | 类型 | 内容 | TTL/用途 |
| --- | --- | --- | --- |
| `agent:task:lease:{taskId}` | Hash | `workerId`、`generation`、`leaseUntil` | 租约时长 + 60 秒，过期用于快速告警 |
| `agent:task:heartbeat:{taskId}` | String | `workerId:generation:timestamp` | 90 秒，判断 Worker 是否仍存活 |
| `agent:task:cancel:{taskId}` | String | `generation` | 任务取消或重置时写入，Worker 轮询后立即停止 |

Worker 每 15 秒发送一次心跳，并在租约剩余时间小于 2 分钟时续期。续期必须同时校验任务状态、Worker 身份和执行代次，不能只按任务 ID 更新：

```sql
UPDATE agent_task
SET lease_until = DATE_ADD(NOW(), INTERVAL 5 MINUTE),
    heartbeat_time = NOW(),
    update_time = NOW()
WHERE id = #{taskId}
  AND status = 'RUNNING'
  AND worker_id = #{workerId}
  AND execution_generation = #{generation}
  AND lease_until > NOW()
  AND deleted = 0;
```

影响行数为 `0` 时，Worker 立即停止写文件、提交和推送，并进入进程组终止及 Worktree 清理。控制面每 30 秒执行一次超时扫描：

1. 在短事务中使用 `FOR UPDATE SKIP LOCKED` 锁定过期任务，递增 `execution_generation`，清空 `worker_id` 和租约，并将状态改为 `FAILED`，错误原因写入审计日志。
2. 事务提交后向旧 Worker 发送取消信号，按记录的 Worker ID 清理进程组和工作区；清理失败保留失败状态，交由补偿任务重试。
3. 只有人工点击“重新执行”或调用显式重投接口后，任务才会生成新的执行代次并回到 `PENDING`，旧 Worker 即使网络恢复也无法通过代次校验写回结果。

### 3.3 重置状态（Reset）彻底回滚实现
当任务在 `PAUSED` 状态下触发 `resetTask` 时，先以条件更新将任务置为 `RESETTING`，再执行外部资源清理。这样可以阻止重复点击和调度竞态；清理操作必须幂等，即工作区、分支或进程已经不存在时仍可继续完成。

```java
public void resetTask(Long taskId, boolean keepPaused) {
    // 事务一：只做状态抢占和快照，毫秒级提交
    ResetContext context = transactionTemplate.execute(status -> {
        AgentTaskDO task = taskMapper.selectById(taskId);
        if (task == null || !"PAUSED".equals(task.getStatus())) {
            throw exception(TASK_CANNOT_RESET_NOT_PAUSED);
        }
        if (taskMapper.markResettingIfPaused(taskId) != 1) {
            throw exception(TASK_RESET_IN_PROGRESS);
        }
        return new ResetContext(task.getTaskNo(), task.getWorkerId(), task.getTargetBranch(), keepPaused);
    });

    // 事务外执行可重复的进程、Worktree 和远端分支清理
    processManager.killProcessGroupIfPresent(context.workerId());
    worktreeManager.destroyCompositeWorkspaceIfPresent(context.taskNo());
    for (AgentTaskProjectDO project : taskProjectMapper.selectListByTaskId(taskId)) {
        gitApiOperator.deleteBranchIfExists(project.getProjectCode(), context.targetBranch());
    }

    // 事务二：清空执行痕迹；失败时保留 RESETTING 交给补偿任务
    transactionTemplate.executeWithoutResult(status -> taskMapper.finishReset(
        taskId, context.keepPaused() ? "PAUSED" : "PENDING"));
}
```

`markResettingIfPaused` 必须使用 `WHERE id = ? AND status = 'PAUSED' AND deleted = 0`；任何清理步骤失败都要记录错误并保留 `RESETTING` 状态，由补偿任务继续清理，不能直接伪装成 `PENDING`。如果产品提供“重置后保持暂停”选项，最终状态改为 `PAUSED`，其他清理规则不变。

`finishReset` 必须带 `WHERE id = ? AND status = 'RESETTING'`，并清空日志、Diff、重试次数、耗时、工作区、Worker 和租约字段；任一步外部清理失败都保留 `RESETTING`，由补偿任务继续执行。这样不会让数据库事务长时间包住远程 Git API、进程终止或磁盘删除操作。

```
├── .ai/
│   ├── task.md                 # 原始任务文档
│   └── WORKFLOW.md             # 系统级执行约束
├── backend/                    # backend-service 的 Git Worktree
└── frontend/                   # frontend-portal 的 Git Worktree
```

`WorktreeManager` 的创建流程：

1. 校验 `project_code`、`base_branch` 和 `sub_dir`；`sub_dir` 必须是根目录下的安全相对路径，拒绝 `..`、绝对路径和重复目录。
2. 确认项目裸仓库缓存存在，不存在时执行一次 `git clone --bare`；随后执行 `git fetch origin <baseBranch>` 获取最新基线。
3. 在聚合根目录下为每个项目执行 `git worktree add -b <targetBranch> <root>/<subDir> refs/heads/<baseBranch>`，记录实际路径和分支。裸仓库缓存按 `git clone --bare` 布局把基线直接保存为 `refs/heads/<baseBranch>`，因此起点引用本地分支而非 `origin/<baseBranch>`。
4. 将任务文档和 `WORKFLOW.md` 写入 `.ai` 目录，校验文件写入完成后才启动 Codex。

清理流程必须支持重复执行：先停止任务进程，再执行 `git worktree remove --force`、物理目录删除和 `git worktree prune`。创建过程中任一步失败时，按已成功挂载的项目倒序清理，避免留下半成品目录。正常合并完成后依次回收聚合工作区、各项目的本地与远端特性分支以及裸仓库缓存，全部清理完成后才进入 `COMPLETED`；重置操作只回收聚合工作区与特性分支。

### 3.5 CodexRunner 与自验闭环

`CodexRunner` 只接受已经通过 Front Matter 和项目资产校验的任务，执行边界如下：

* 以非交互批处理模式启动 Codex，工作目录固定为聚合根目录，禁止等待终端人工输入。
* 实时读取 stdout/stderr，追加写入 `execution_log`，同时按阶段记录 `PREPARE`、`CODING`、`VERIFYING`、`PUBLISHING` 和 `CLEANUP`。
* 串行执行任务文档中的所有验收命令；任意命令非零退出都不能提交或推送代码。
* 测试失败时允许根据错误输出自我修复，最多 2 次；超过次数后标记 `FAILED`，保留最后一次上下文和完整日志。
* 所有验收命令通过后，检查变更范围、生成 `git diff --stat` 和 `workpad_summary.json`，再按项目执行 `git add`、提交和 `git push`。禁止 `force push`。
* 使用进程组和硬超时控制整个 Codex、编译器及测试树；超时必须终止进程组、回收工作区并标记 `FAILED`。

### 3.6 通知、验收与多仓合并

Worker 完成自验后，将任务置为 `WAITING_ACCEPTANCE`，回传包含任务编号、各仓分支链接、修改文件、Diff 统计、测试命令及结果、重试次数和耗时的结构化报告。Webhook 发送应带幂等键 `taskNo + reportVersion`，重复投递不能产生重复卡片或重复执行。

验收回调必须再次校验任务当前状态和操作人权限：只有 `WAITING_ACCEPTANCE` 可以转为 `ACCEPTED` 或 `REJECTED`，重复点击只返回当前结果。接受后先对所有代码仓执行目标分支可合并性检查，任一仓冲突则置为 `MERGE_CONFLICT_PENDING_MANUAL`，不得先合并其他仓；全部通过后才调用 GitLab/GitHub/Gitea API 执行 Fast-Forward 或 Squash Merge。每个项目的合并结果写入 `agent_task_project.merge_status`，全部成功后再回收聚合工作区、特性分支与裸仓库缓存，全部清理完成后任务才进入 `COMPLETED`。

卡片验收/打回回调为公开 Webhook `POST /admin-api/agent/notice/callback`：请求头 `X-TaskForge-Timestamp`、`X-TaskForge-Nonce`、`X-TaskForge-Signature` 先通过 HMAC-SHA256 签名与回放校验；请求体为 `{taskNo, action(accept|reject), reportVersion, feedback?, token}`，其中 `token = HMAC-SHA256(secret, taskNo + "\n" + action + "\n" + reportVersion)`，只映射到指定任务、动作与报告版本。回调按任务编号解析主键后复用控制面 `accept` / `reject` 入口，并以令牌作为幂等键；非 `WAITING_ACCEPTANCE` 状态只返回当前结果。响应为 `{success, retryable, taskNo, status, operationId, message}`：成功返回 `200`，永久失败返回 `4xx`，瞬时失败返回 `500` 且 `retryable=true` 供卡片平台重试。

### 3.7 控制面 API 与状态转换约束

| 方法 | 路径 | 允许的前置状态 | 作用 |
| --- | --- | --- | --- |
| `POST` | `/api/v1/tasks/submit` | 无 | 解析并校验 Markdown，创建 `PENDING` 任务 |
| `GET` | `/api/v1/tasks` | 任意 | 按任务编号、状态、优先级和创建时间查询，默认过滤软删除 |
| `POST` | `/api/v1/tasks/{id}/pause` | `PENDING` | 暂停任务并阻止调度 |
| `PATCH` | `/api/v1/tasks/{id}/document` | `PAUSED` | 携带 `docVersion` 更新文档和执行参数 |
| `POST` | `/api/v1/tasks/{id}/resume` | `PAUSED` | 重新校验文档后恢复为 `PENDING` |
| `POST` | `/api/v1/tasks/{id}/cancel` | `PENDING`、`PAUSED` | 冻结任务并记录取消原因 |
| `POST` | `/api/v1/tasks/{id}/reset` | `PAUSED` | 进入 `RESETTING`，清理资源后回到 `PENDING` |
| `POST` | `/api/v1/tasks/{id}/re-enqueue` | `CANCELED`、`REJECTED`、`FAILED` | 原位恢复或克隆生成新任务 |
| `POST` | `/api/v1/tasks/{id}/accept` | `WAITING_ACCEPTANCE` | 触发多仓合并预检和合并流程 |
| `POST` | `/api/v1/tasks/{id}/reject` | `WAITING_ACCEPTANCE` | 记录反馈并转为 `REJECTED`，等待重新派发 |
| `POST` | `/api/v1/tasks/{id}/merge-conflict` | `ACCEPTED` | 标记合并冲突，转入 `MERGE_CONFLICT_PENDING_MANUAL` 等待人工处理 |
| `DELETE` | `/api/v1/tasks/{id}` | `CANCELED` | 执行软删除并保留审计记录 |
| `GET` | `/api/v1/tasks/{id}/diff` | `WAITING_ACCEPTANCE` 及终态 | 获取 Diff、测试报告和执行日志摘要 |

所有变更接口都必须在服务端重新读取任务状态，使用条件更新保证幂等；不能信任前端传入的状态。文档更新必须携带当前 `docVersion`，版本不一致返回 `409 Conflict`。验收、重置和删除接口需要记录操作人及请求幂等键，重复请求返回第一次执行结果。

### 3.8 REST DTO、幂等键与错误响应

控制面接口统一使用 JSON，写操作要求请求头 `X-Idempotency-Key`（长度 16-128，仅允许字母、数字、`.`、`_`、`-`）。同一租户、同一任务和同一幂等键只执行一次；重复请求返回第一次操作的结果。投递（submit）时任务尚未创建，因此同一租户内幂等键通过 `agent_task_operation_log` 的 `uk_request_key(request_idempotency_key, tenant_id)` 唯一键去重，保证重复投递不会重复建任务。编辑文档另外要求请求头 `If-Match: <docVersion>`，不匹配时返回 `409`，响应中带最新版本号。

```java
public record SubmitTaskRequest(
    @NotBlank @Size(max = 200_000) String document
) {}

public record UpdateTaskDocumentRequest(
    @NotNull @Min(1) Integer docVersion,
    @NotBlank @Size(max = 200_000) String document,
    @Min(1) @Max(1440) Integer timeoutMinutes,
    @Min(0) @Max(1000) Integer priority,
    Long dependsOnTaskId
) {}

public record RejectTaskRequest(
    @NotBlank @Size(max = 2000) String feedback
) {}

public record TaskOperationResponse(
    Long taskId,
    String taskNo,
    String status,
    Integer docVersion,
    Long executionGeneration,
    String operationId
) {}
```

`POST /api/v1/tasks/submit` 的成功响应示例：

```json
{
  "taskId": 9012,
  "taskNo": "TASK-20261001-088",
  "status": "PENDING",
  "docVersion": 1,
  "executionGeneration": 0,
  "operationId": "op_01J..."
}
```

参数校验、Front Matter 解析和项目资产校验失败统一返回 `400`；无权限返回 `403`；任务不存在或租户不匹配返回 `404`；状态条件不满足返回 `409`；服务端异常返回 `500` 并携带可追踪的 `traceId`。错误响应不得回显 Git 凭证、完整环境变量或未脱敏的执行日志。

### 3.9 完整状态转换矩阵与条件更新

状态转换只能由服务端动作触发，前端不能直接提交目标状态。下表是允许的最小转换集合；未列出的组合一律拒绝并返回 `409`：

| 当前状态 | 动作 | 目标状态 | 触发方 | 约束 |
| --- | --- | --- | --- | --- |
| `PENDING` | `PAUSE` | `PAUSED` | 用户 | 仅条件更新成功才返回成功 |
| `PENDING` | `CLAIM` | `RUNNING` | 调度器 | 校验依赖已完成、租约和执行代次 |
| `PENDING` | `CANCEL` | `CANCELED` | 用户 | 写入取消原因和审计 |
| `PAUSED` | `EDIT` | `PAUSED` | 用户 | `docVersion` 乐观锁 |
| `PAUSED` | `RESUME` | `PENDING` | 用户 | 重新校验文档和项目 |
| `PAUSED` | `RESET` | `RESETTING` | 用户 | 进入清理流程，禁止重复操作 |
| `PAUSED` | `CANCEL` | `CANCELED` | 用户 | 冻结文档 |
| `RUNNING` | `SELF_VERIFY_PASS` | `WAITING_ACCEPTANCE` | Worker | 所有验收命令退出码为 0 |
| `RUNNING` | `TIMEOUT/ERROR` | `FAILED` | Worker/恢复器 | 终止进程组并保留日志 |
| `WAITING_ACCEPTANCE` | `ACCEPT` | `ACCEPTED` | 用户/Webhook | 校验验收权限和幂等键 |
| `WAITING_ACCEPTANCE` | `REJECT` | `REJECTED` | 用户/Webhook | 必须有反馈 |
| `ACCEPTED` | `MERGE_PASS` | `COMPLETED` | 合并器 | 所有仓合并成功且资源清理完成后才允许 |
| `ACCEPTED` | `MERGE_CONFLICT` | `MERGE_CONFLICT_PENDING_MANUAL` | 合并器 | 任何仓冲突都阻断其他仓 |
| `REJECTED`/`FAILED` | `RE_ENQUEUE` | `PENDING` | 用户 | 生成新的执行代次 |
| `CANCELED` | `RE_ENQUEUE` | `PENDING` | 用户 | 原位恢复或克隆新任务 |
| `CANCELED` | `DELETE` | `DELETED` (`deleted=1`) | 用户 | 仅软删除，审计不可删除 |
| `RESETTING` | `CLEANUP_PASS` | `PENDING`/`PAUSED` | 补偿任务 | 根据重置选项决定 |

条件更新示例：

```sql
UPDATE agent_task
SET status = 'PAUSED', update_time = NOW()
WHERE id = #{taskId} AND status = 'PENDING' AND deleted = 0;

UPDATE agent_task
SET status = 'PENDING', doc_version = doc_version + 1, update_time = NOW()
WHERE id = #{taskId} AND status = 'PAUSED'
  AND doc_version = #{expectedVersion} AND deleted = 0;

UPDATE agent_task
SET status = 'WAITING_ACCEPTANCE', lease_until = NULL,
    heartbeat_time = NULL,
    execution_log = #{executionLog},
    retry_times = #{retryTimes},
    cost_ms = #{costMs},
    diff_stat = #{diffStat},
    workspace_path = #{workspacePath},
    update_time = NOW()
WHERE id = #{taskId} AND status = 'RUNNING'
  AND worker_id = #{workerId}
  AND execution_generation = #{generation};

UPDATE agent_task
SET status = 'FAILED', worker_id = NULL, lease_until = NULL,
    heartbeat_time = NULL,
    execution_log = #{executionLog},
    retry_times = #{retryTimes},
    cost_ms = #{costMs},
    diff_stat = #{diffStat},
    workspace_path = NULL,
    finished_time = NOW(),
    update_time = NOW()
WHERE id = #{taskId} AND status = 'RUNNING'
  AND worker_id = #{workerId}
  AND execution_generation = #{generation};
```

`SELF_VERIFY_PASS`、`TIMEOUT`、`ERROR` 三条 Worker 写回动作除状态外，还会在同一条件更新中写回执行日志、重试次数、耗时、Diff 统计与工作区路径；失败路径清空 `workspace_path`，并在写回前幂等清理聚合工作区与特性分支（失败清理）。执行编排器 `AgentTaskExecutor` 在 Codex 单次尝试硬超时时触发熔断：终止整个进程组并立即进入 `FAILED`，不再进入后续自修复重试。

每条成功的条件更新必须在同一事务内插入 `agent_task_operation_log`，并使用 `(task_id, request_idempotency_key, tenant_id)` 唯一键防止重复操作；投递操作另外依赖 `uk_request_key(request_idempotency_key, tenant_id)` 跨任务去重。远程通知和 Git API 调用放在事务提交后执行，失败由 Outbox 或补偿任务重试。

### 3.10 凭证、Webhook、权限与路径安全

* **Git 凭证**：`git_url` 可以保存地址，但 Token、SSH 私钥和密码只能保存于部署环境的 Secret Manager（或加密配置中心）；数据库只保存 `credential_ref`。Worker 启动时按引用读取短期凭证，日志中对 URL、Header、命令参数执行脱敏，禁止把凭证写入 `.ai` 文件。
* **Webhook 签名**：发送卡片时在请求头写入 `X-TaskForge-Timestamp`、`X-TaskForge-Nonce` 和 `X-TaskForge-Signature`，签名内容为 `timestamp + "\\n" + nonce + "\\n" + rawBody`，使用 HMAC-SHA256；接收回调时校验时间窗口（默认 5 分钟）、签名和幂等键，拒绝重放。
* **接口权限**：任务读取、编辑、验收和删除都校验租户隔离、项目权限和操作人角色。Webhook 回调不能绕过权限，回调 Token 只映射到指定任务和指定动作。
* **路径安全**：`workspace_path` 只能由服务端根据不可预测的任务编号生成，禁止接受客户端绝对路径；`subDir` 经过 `Path.normalize()` 后必须仍位于聚合根目录内，拒绝 `..`、符号链接、NUL 字符和路径分隔符混用。执行命令只能来自通过白名单校验的项目配置或文档验收步骤，禁止拼接未经转义的用户输入。
* **资源限制**：Docker/Cgroups 配置 CPU、内存、进程数、磁盘配额和网络策略；容器以非 root 用户运行，工作区挂载为最小权限，任务结束后销毁容器和临时凭证。

### 3.11 测试与验收清单

实现完成后至少通过以下测试门禁，测试结果写入 `workpad_summary.json` 并在控制台展示：

1. **单元测试**：Front Matter 解析、必需小节校验、状态机非法转换、幂等键重复请求、文档版本冲突、路径穿越和 Webhook 签名校验。
2. **MySQL 集成测试**：使用 MySQL 8 容器启动两个调度线程，验证 `SKIP LOCKED` 不重复消费；验证前置任务未完成时不会被抢占；验证条件更新影响行数和审计记录一致。
3. **Redis 集成测试**：验证租约 TTL、心跳续期、取消键传播、租约过期后的恢复以及旧执行代次不能写回结果。
4. **Worktree 测试**：创建单仓和多仓聚合工作区，模拟中途失败、重复清理、分支已删除和符号链接目录，确保最终没有残留进程、目录或挂载。
5. **Worker 端到端测试**：用假的 Codex CLI 覆盖成功、编译失败后两次自修复、超时、非零退出码、日志截断和禁止 `force push` 等路径。
6. **接口与权限验收**：覆盖控制台和 Webhook 两个验收入口，验证重复点击、跨租户访问、无权限操作、合并冲突阻断和软删除隐藏规则。

上线前验收标准：连续运行 24 小时无租约泄漏；所有失败任务都能通过日志和 `traceId` 定位；重启控制面或 Worker 后不产生重复提交；多仓合并满足全有或全无；`git diff --check`、后端测试、前端类型检查和构建命令全部通过。

## 4. Symphony 提示词规范（Prompts 约束设计）

在挂载的工作区根目录下自动渲染并生成 `.ai/WORKFLOW.md`。借鉴 Symphony SPEC 的设计思想，通过严密的系统级提示词规范 Codex 的行为：

````markdown
# Role and Execution Protocol for Coding Agent

You are Symphony-Agent, an automated developer running within an isolated workspace.
Your mission is to read and fulfill the execution requirements specified in `.ai/task.md`.

## Execution Rules (STRICT):
1. **Scope Restriction**: Modify ONLY files within the subprojects listed under `projects` in `.ai/task.md`. Never make any changes outside these directory boundaries.
2. **Phase 1: Implementation**:
   - Read the Execution Plan carefully.
   - For multi-project tasks (e.g. backend and frontend), ensure that API endpoints, DTO models, and parameter names match precisely between frontend client calls and backend controllers.
3. **Phase 2: Verification (Non-Negotiable)**:
   - Once code changes are made, run the exact bash commands defined in `Verification Steps` of `.ai/task.md`.
   - If any test or build fails, read the terminal output, reason through the root cause, and correct your implementation.
   - You are permitted up to 2 self-correction iterations.
4. **Phase 3: Workpad Summary**:
   - Generate a concise summary of changes and validation test results into `.ai/workpad_summary.json` following this format:
      ```json
     {
       "allPassed": true,
       "testsExecuted": ["mvn test -Dtest=OrderTest", "pnpm test"],
       "modifiedFiles": ["backend/src/...", "frontend/src/..."],
       "notes": "Added coupon deduction validation and UI bindings."
     }
      ```
5. **Commit Gate**: Do not run `git commit` or `git push` until every verification command exits with code `0`; never use `git push --force`.
6. **No Terminal Prompts**: Run commands in non-interactive batch mode. Do NOT pause to wait for human confirmation.
7. **Result Contract**: If verification fails after the allowed retries, write the failure details to `.ai/workpad_summary.json` and exit non-zero so the controller marks the task `FAILED`.

````

## 6. 实施路线与演进计划

1. **里程碑 1：数据底座与模块脚手架（1-2 周）**
* 在 `ruoyi-vue-pro` 中引入 `yudao-module-agent` 骨架及相关表结构（V1.0 Flyway/SQL 脚本）。
* 实现 `agent_project` 基础 CRUD，完成 Git 裸库缓存池的本地初始化机制。
* 建立任务、项目和任务-项目映射表的唯一索引、租约字段和审计字段。


2. **里程碑 2：任务控制面与状态流转（2-3 周）**
* 实现 HTTP API 接收本地投递 Markdown 文档并自动解析 FrontMatter。
* 完成基于 MySQL `FOR UPDATE SKIP LOCKED` 的调度器。
* 完整落地 `PAUSED`、`RESUME`、`CANCEL`、`RESET`、`REJECTED`、合并冲突和软删除逻辑。
* 增加文档版本乐观锁、优先级/前置任务依赖校验、Worker 租约续期和状态转换审计。


3. **里程碑 3：Worktree 聚合沙箱与 Codex 驱动闭环（3-4 周）**
* 编写 `WorktreeManager`，实现多仓子目录聚合挂载与清理。
* 集成 Symphony 规范的 `.ai/WORKFLOW.md` 提示词，实现 Codex CLI 非交互子进程运行、日志抓取与自验测试指令执行。
* 增加 Docker/Cgroups 资源限制、进程组硬超时、最多 2 次自修复重试和失败补偿清理。


4. **里程碑 4：通知集成与自动化合并（4-5 周）**
* 联调企业微信/飞书卡片 Webhook 发送。
* 对接 GitLab/GitHub/Gitea API，完成多仓合并预检、Fast-Forward/Squash Merge、冲突挂起和幂等回调。
* 上线 `yudao-ui-admin-vue3` 完整控制台，补齐 Diff、日志、测试报告、重置确认和打回反馈视图。


5. **里程碑 5：安全加固与可观测性（1-2 周）**
* 接入 Secret Manager，完成 Git 凭证引用、日志脱敏、Webhook HMAC 签名和回放防护。
* 落地 Docker/Cgroups 限额、工作区路径校验、进程组清理和租约过期补偿任务。
* 为任务、Worker、Webhook 和 Git API 调用补齐 `traceId`、结构化日志、耗时和失败原因指标。


6. **里程碑 6：测试门禁与灰度上线（2 周）**
* 完成状态机、Front Matter、幂等、权限、路径安全和签名单元测试，以及 MySQL/Redis/Testcontainers 集成测试。
* 完成 Worktree 生命周期、Codex 假进程、超时恢复、多仓合并冲突和控制台端到端测试。
* 先在单 Worker、单租户和非生产仓库灰度运行 24 小时，确认无重复提交、租约泄漏或残留进程后再扩大并发。
